# 01. 平台架构与 Vela QuickApp 渲染引擎深度剖析

> 本章重点帮助开发者建立对 **Xiaomi Vela OS** 底层环境与 **穿戴式快应用渲染引擎** 的真实认知，彻底破除“手环开发等于普通 Web 开发”的思维误区。

---

## 一、小米手环系统底座演进

小米智能穿戴设备的底层操作系统经历了三个主要阶段：
1. **早期微控制器 RTOS 阶段（小米手环 1~6）**：单片机纯 C/C++ 裸机或极简 RTOS，业务完全固化于固件中，无动态第三方应用生态。
2. **轻量富图形阶段（小米手环 7~8 标准版）**：基于 Dialog / 恒玄平台，支持基础表盘定制与静态资源打包，部分引入简易卡片框架。
3. **Xiaomi Vela OS / HyperOS 统一生态（小米手环 8 Pro / 9 / 9 Pro 及 S 系列手表）**：
   - **底座内核**：基于 Apache NuttX 实时微内核打造的 **Xiaomi Vela**，统一跨芯片物联网设备（IoT）。
   - **应用层载体**：全面引入基于 QuickApp（快应用）规范的穿戴轻应用框架，支持以声明式前端语法（UX 文件）构建原生级穿戴应用。
   - **动态分发**：支持 `.rpk` 压缩归档格式，实现无需刷入整包固件的独立应用在线安装、更新与卸载。

## 二、QuickApp C++ Lite 引擎的运转机制

很多刚接触手环开发的工程师最容易犯的错误是：**误以为手环里跑的是 Chromium / Android WebView / Node.js V8 引擎。**

### 1. 真实运行模型
在 Xiaomi Vela 上，快应用的执行引擎是一个专为嵌入式硬件高度裁剪的 **C++ Lite 轻量引擎**：
- **无完整 DOM 树**：底层并不维护 HTML DOM 树，而是由 C++ 渲染树直接对接嵌入式 2D 图形库（如 LVGL / 深度裁剪的 Skia / 自研渲染管线）进行矢量及位图栅格化绘制。
- **裁剪版 JS 解释器**：通常使用 JerryScript、QuickJS 或轻量 V8 变种，内存占用严格控制在几百 KB 以内。
- **零浏览器全局对象**：不存在 `window`、`document`、`navigator`、`localStorage`、`fetch`、`XMLHttpRequest` 等浏览器环境特有对象。
- **点对点硬件加速**：UI 组件直接映射为穿戴屏幕图层，以 60Hz 垂直同步（VSync）刷新，确保小屏滑动的丝滑手感。

```
┌────────────────────────────────────────────────────────┐
│           开发者编写的 UX 代码 (.ux / JS / CSS)          │
└────────────────────────────────────────────────────────┘
                           │  (aiot-toolkit Webpack 编译打包)
                           ▼
┌────────────────────────────────────────────────────────┐
│       RPK 安装包 (Bytecode / JSON AST / 静态资源)        │
└────────────────────────────────────────────────────────┘
                           │  (蓝牙侧载 / 系统运行时加载)
                           ▼
┌────────────────────────────────────────────────────────┐
│             Vela QuickApp C++ Lite Runtime             │
│  ├── JS 解释器 (执行业务逻辑 / 数据响应式绑定)           │
│  ├── C++ 渲染管线 (Flexbox 布局计算 / 文字与图形绘制)   │
│  └── 原生系统服务桥接 (@system.storage / vibrator 等)  │
└────────────────────────────────────────────────────────┘
                           │
                           ▼
┌────────────────────────────────────────────────────────┐
│          NuttX RTOS 内核 / 硬件帧缓冲区 (FrameBuffer)   │
└────────────────────────────────────────────────────────┘
```

## 三、主流硬件规格与物理约束矩阵

在动手编写 UI 之前，必须对目标设备的物理参数了然于胸：

| 设备型号 | 屏幕类型 | 分辨率 (W × H) | 屏幕形态 | 典型可用 RAM 预算 | 适用场景 |
| :--- | :--- | :--- | :--- | :--- | :--- |
| **小米手环 9 Pro** | AMOLED | **336 × 480** | 矩形微曲面 | **极度紧缺 (几百 KB ~ 数 MB)** | **全功能应用（记事本、计算器、工具）** |
| **小米手环 8 Pro** | AMOLED | **336 × 480** | 矩形微曲面 | 极度紧缺 | 适用同套 336px 设计规范 |
| **小米手环 9 标准版** | AMOLED | **192 × 490** | 细长药丸跑道屏 | 极度紧缺 | 适合轻量仪表卡片、简单列表 |
| **小米手表 S 系列** | AMOLED | **466 × 466** | 正圆形屏幕 | 较充裕 | 圆形 UI 规范、全功能表盘 |

### 关键硬件特性影响：
1. **微曲面边缘切角**：手环 9 Pro 四周为 2.5D 微曲面玻璃，贴边 10~14px 区域不仅有视觉畸变，且触控电容感应灵敏度下降，所有关键交互必须留出边距。
2. **AMOLED 功耗定律**：发光机制为像素自发光，纯黑 `#000000` 像素点完全关闭，功耗接近 0；大面积白色背景会呈指数级加速掉电并引起手环局部发热。
3. **触觉马达（Linear Haptic Motor）**：手环小屏幕敲击缺乏机械行程，必须依赖振动反馈赋予用户物理确认感。

## 四、穿戴应用的生命周期与“无后台”铁律

手环操作系统的第一优先级是：**续航保卫战与时间/健康监测稳定性**。

### 1. 穿戴应用的生命周期流转
```
              启动应用 (onCreate)
                     │
                     ▼
              前台显示 (onShow) ◄──────┐
                     │                 │
              [ 用户正常操作应用 ]     │
                     │                 │ 用户重新点亮屏幕
        息屏 / 来电 / 短按侧键退回     │
                     │                 │
                     ▼                 │
              转入后台 (onHide) ───────┘
                     │
                     ▼ (内存紧张或超时立即强杀)
              应用销毁 (onDestroy)
```

### 2. 核心红线：“无后台常驻”
- **切勿心存侥幸**：永远不要假设手环应用可以在后台长期运行定时器或网络轮询。
- **随时可能猝死**：用户手掌覆盖息屏、手腕自然下垂或收到一条高优先级的系统通知，手环系统会瞬间触发 `onHide`，紧接着为保证表盘流畅，可能在数秒内直接销毁（Kill）快应用进程。
- **铁律结论**：**状态变动必须即时落盘（Instant Persistence）**，所有未存盘的内存数据都会在息屏瞬间灰飞烟灭。
